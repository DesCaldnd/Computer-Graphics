# OxwaldEngine — план развития

Oct 8, 2026 · @Oxwald

## Цели и исходная точка

Движок переезжает с OpenGL на Vulkan первым же шагом, а RTX включается галочкой в настройках поверх общего растрового рендера. Отражения и волюметрика есть в обоих режимах: в растре через экранные и пробные техники, в RTX через лучи.

**Принципы**

- Растровый путь — основной и работает на любой GPU с Vulkan 1.3. RTX-путь — надстройка: те же сцены, материалы и проходы, меняется только реализация части эффектов.
- Галочка «Трассировка лучей» активна, только если устройство поддерживает `VK_KHR_acceleration_structure` и `VK_KHR_ray_query`. Иначе она серая с подсказкой, почему.
- Переключение без перезапуска: render graph пересобирается, сцена и ассеты остаются.
- Сначала замеры, потом оптимизации: Tracy и RenderDoc подключаются в фазе 1.

**Что есть сейчас** (репозиторий `DesCaldnd/Computer-Graphics`, около 3 300 строк)

- Qt + OpenGL, шейдеры GLSL 130, тени с ручной упаковкой глубины в RGBA, максимум 5 источников.
- Точечный свет наполовину сделан: тип есть, геометрический шейдер cubemap-теней написан, но выключен.
- Bullet подключён, мир симуляции закомментирован, синхронизация через углы Эйлера.
- Кривая Безье лежит в `Test`, а не в движке.
- `Scene.cpp` (\~1 000 строк) отвечает за рендер, ввод, редактор и физику сразу.

Старый GL-рендер не портируется построчно: он заменяется новым, а из него берутся только идеи (PCF, пикинг по цвету, скайбокс).

## Фаза 0–1. Переход на Vulkan

Итог фазы: сцена из старого проекта рисуется на Vulkan с PBR-материалами, тенями от направленного света и пикингом объектов в редакторе.

**Фаза 0. Подготовка (1–2 недели)**

1. Перевести сборку на CMake presets + vcpkg или Conan, C++20.
2. Подключить библиотеки: Vulkan SDK, `volk` (загрузка функций), VulkanMemoryAllocator, `vk-bootstrap` (инициализация), glm, shaderc или Slang для компиляции шейдеров в SPIR-V.
3. Включить validation layers и `VK_EXT_debug_utils` с именами объектов: без этого отладка Vulkan превращается в угадайку.
4. Подключить Tracy (CPU и GPU-зоны) и проверить, что кадр видно в RenderDoc.

**Фаза 1. Новый рендер**

1. **RHI** — тонкий слой над Vulkan: `Device`, `Buffer`, `Texture`, `Pipeline`, `CommandList`, `Fence`. Он не прячет Vulkan полностью, но не даёт `VkXxx` расползтись по игровому коду.
2. **Интеграция с Qt**: `QVulkanInstance` + `QWindow` внутри `QWidget::createWindowContainer`, чтобы редактор на Qt остался. Swapchain, пересоздание при ресайзе, 2–3 кадра в полёте.
3. **Dynamic rendering и bindless**: Vulkan 1.3 без render pass объектов; один большой descriptor set с массивом текстур и буферов (descriptor indexing). Материал хранит индексы текстур, а не биндинги.
4. **Render graph**: проходы объявляют, что читают и пишут; граф сам ставит барьеры, переходы layout и алиасит память временных текстур. Именно граф позволит потом включать RTX-проходы галочкой.
5. **Ресурсы**: загрузка мешей через assimp (позже свой бинарный формат), текстуры в KTX2, кольцевые upload-буферы, отдельная transfer-очередь.
6. **Перенос функций**: G-buffer или forward+, скайбокс, тени через depth-текстуры с аппаратным сравнением, пикинг через ID-буфер.
7. **Hot reload шейдеров**: изменился файл → пересборка pipeline без перезапуска.

Риски: Vulkan многословен, первый треугольник займёт заметно больше времени, чем в GL. Не стоит строить идеальный RHI заранее: абстракции добавляются, когда второй проход требует того же, что первый.

## Фаза 2. Архитектура и физика

Итог фазы: объекты — это сущности ECS, `Scene` разрезан на сервисы, физика работает с фиксированным шагом.

1. **ECS на EnTT**. Компоненты-данные: `Transform`, `MeshRenderer`, `Light`, `Camera`, `RigidBody`, `Collider`, `Script`, `Spline`. Системы: трансформы (иерархия), рендер-экстракт, физика, скрипты. Иерархия `LightObject : MeshObject` исчезает.
2. **Сервисы и DI**: `Renderer`, `PhysicsWorld`, `AssetManager`, `Input`, `Audio`, `Editor` регистрируются в контейнере и передаются системам, а не достаются через глобальный `Scene*`.
3. **Игровой цикл**: фиксированный шаг для физики и логики (например, 60 Гц), интерполяция трансформов для рендера, переменный шаг для кадра.
4. **Разделение потоков**: игровой поток пишет снимок сцены (render extract), рендер-поток рисует предыдущий. Это основа для всех будущих оптимизаций.
5. **Физика на Jolt** (рекомендуется) или на уже подключённом Bullet. Jolt многопоточен из коробки и проще в интеграции; PhysX для такого движка тяжеловат. Синхронизация через кватернионы, не через углы Эйлера.
6. **Коллайдеры** как компоненты с редактированием в инспекторе: box, sphere, capsule, convex hull, triangle mesh для статики. Триггеры (overlap), raycast-запросы, character controller.
7. **Debug draw**: линии коллайдеров, нормалей, AABB — общий сервис, которым пользуются физика, сплайны и редактор.
8. **Сериализация сцены** в JSON (уже есть nlohmann) через рефлексию компонентов, чтобы инспектор и сохранение не писались вручную для каждого поля.

## Фаза 3. Свет, отражения и волюметрика (растр)

Итог фазы: десятки источников с тенями, физически корректные материалы, отражения, объёмный свет, прозрачность и преломления без RTX.

**Освещение и тени**

- PBR по модели metallic-roughness (GGX, Smith, Schlick), HDR-буфер и тонмаппинг (ACES или AgX).
- Clustered forward+ или deferred: источники в SSBO, разбивка кадра на кластеры compute-шейдером. Лимит в 5 источников исчезает.
- Точечные источники: cubemap-тени через multiview или layered rendering, затухание по обратному квадрату с радиусом отсечения.
- Прожекторы: обычная перспективная тень, мягкий край по конусу (как сейчас `cutoff` и `soft`).
- Направленный свет: cascaded shadow maps (4 каскада), стабилизация от дрожания.
- Атлас теней: источники получают разрешение по важности и расстоянию, статичные не перерисовываются каждый кадр.
- Мягкие тени: PCF с Poisson-выборками или PCSS.
- IBL из скайбокса: префильтрованная cubemap для бликов, irradiance для рассеянного, BRDF LUT.

**Отражения**

1. Reflection probes: кубкарты, расставленные в сцене, с коррекцией по параллаксу (box projection). Запекаются в редакторе, могут обновляться в рантайме по одной грани за кадр.
2. SSR (экранные отражения): трассировка по Hi-Z буферу глубины, фолбэк на пробы там, где луч ушёл за экран.
3. Плоские отражения для воды и зеркал: отдельный рендер с отражённой камерой.

**Волюметрика**

1. Froxel-туман: 3D-текстура (например, 160×90×64), привязанная к фрустуму камеры. Compute-шейдер считает плотность, рассеяние от всех источников с учётом теней, затем интеграция вдоль луча.
2. Фазовая функция Henyey-Greenstein для направленного рассеяния (свет «пробивает» туман против солнца).
3. Локальные объёмы тумана как компонент ECS: коробка или сфера с плотностью и цветом.
4. Временное накопление (temporal reprojection), чтобы убрать шум и полосы.
5. Позже: объёмные облака через ray marching по шумовым текстурам.

**Прозрачность и преломления**

1. Материал получает режимы: непрозрачный, alpha-test (листва, решётки), полупрозрачный, преломляющий. Параметры: прозрачность, IOR, толщина, цвет поглощения.
2. Alpha-test в основном проходе с alpha-to-coverage при MSAA или со стохастическим дизерингом под TAA.
3. Порядко-независимая прозрачность: Weighted Blended OIT (дёшево, без сортировки) как основной путь; сортировка объектов от дальних к ближним как запасной для простых сцен.
4. Полупрозрачные объекты получают свет из тех же кластеров, тени и волюметрический туман (выборка froxel-объёма по глубине пикселя).
5. Преломление в экранном пространстве: отдельный проход после непрозрачной геометрии копирует цветовой буфер в мип-цепочку; стекло и вода смещают выборку по нормали и IOR, шероховатость выбирает размытый мип.
6. Поглощение по закону Бугера — Ламберта по толщине (из меша или из разницы глубин передней и задней граней).
7. Френель по Шлику смешивает отражение (пробы, SSR) и преломление.
8. Вода: нормали из волн, преломление дна, каустики проекционной текстурой, туман под водой.
9. Частицы и дым рисуются в отдельный буфер пониженного разрешения и мягко сводятся с глубиной (soft particles).

## Фаза 4. Режим RTX

Итог фазы: галочка «Трассировка лучей» в настройках заменяет тени, отражения, волюметрику, AO и преломления на лучевые версии; без неё всё работает как в фазе 3.

**Инфраструктура**

1. Проверка поддержки при старте: `VK_KHR_acceleration_structure`, `VK_KHR_ray_query`, по возможности `VK_KHR_ray_tracing_pipeline`. Результат хранится в `DeviceCaps`, галочка в UI зависит от него.
2. BLAS на каждый уникальный меш (статика сжимается compaction), TLAS на кадр из всех экземпляров. Скиннинг и деформации — refit BLAS.
3. Начать с ray query прямо в compute- и fragment-шейдерах: проще, чем полный RT-пайплайн с SBT, и покрывает тени, AO и отражения. RT-пайплайн добавить позже для GI и path tracer.
4. Материалы доступны из лучей через bindless: по индексу экземпляра и примитива достаются UV, нормали и текстуры.
5. Денойзинг: свой SVGF-подобный (временное накопление + À-trous фильтр) или NVIDIA NRD. Без денойзера 1 луч на пиксель выглядит как шум.

**Эффекты в двух режимах**

| Эффект | Растр (галочка выключена) | RTX (галочка включена) |
| --- | --- | --- |
| Тени | Shadow maps, CSM, PCF/PCSS | 1 луч на пиксель к источнику, мягкость по размеру источника, денойз |
| Отражения | Пробы + SSR + плоские | Лучи по roughness (GGX-выборка), один отскок, фолбэк на пробы при большой шероховатости |
| Волюметрика | Froxel-туман с shadow maps | Тот же froxel-объём, но видимость источника в каждом фроксе проверяется лучом: тени от любых объектов, включая вне экрана |
| Ambient occlusion | SSAO / GTAO | RTAO, короткие лучи в полусферу |
| Глобальное освещение | Только IBL и пробы | DDGI (сетка проб, обновляемая лучами) или ReSTIR GI |
| Прозрачность и преломление | Weighted Blended OIT, экранное преломление, поглощение по толщине, Френель | Лучи преломления по закону Снелла с несколькими отскоками внутри объекта, полное внутреннее отражение, цветные тени от стекла, каустики, отражения в стекле видят объекты вне экрана |

**Дальше по желанию**

- ReSTIR DI для сотен источников с тенями.
- Отдельный режим path tracer для эталонного кадра и проверки растра «на глаз».
- Апскейлинг: FSR (открытый) или DLSS, чтобы лучевые эффекты считать в меньшем разрешении.

## Оптимизации

Каждая оптимизация начинается с замера в Tracy или RenderDoc и заканчивается замером после: без цифр непонятно, что помогло.

**GPU**

- GPU-driven rendering: culling и формирование команд в compute, отрисовка через `vkCmdDrawIndexedIndirectCount`. CPU почти не участвует в отрисовке.
- Frustum и occlusion culling (Hi-Z по глубине прошлого кадра), отдельно для каждой тени.
- Meshlets и mesh shaders (`VK_EXT_mesh_shader`) с culling по кластерам; позже — автоматические LOD.
- Async compute: волюметрика, частицы и денойзинг параллельно с графикой.
- Кэш теней для статичных источников, разрешение теней по важности.
- Сжатые текстуры (BC7, BC5 для нормалей), мип-стриминг.
- Эффекты в половинном разрешении + апскейл: SSAO, волюметрика, RT-отражения.

**CPU**

- Job system (например, enkiTS): физика, анимация, culling, extract кадра в потоках.
- Запись command buffer'ов параллельно из нескольких потоков.
- Плотные массивы компонентов ECS и отсутствие аллокаций за кадр (frame allocator).
- Асинхронная загрузка ассетов и сборка pipeline'ов в фоне, pipeline cache на диске.

**Инструменты**

- Tracy — CPU и GPU-зоны, аллокации.
- RenderDoc — разбор кадра, ресурсы, шейдеры.
- Nsight Graphics — профилирование RT и occupancy на NVIDIA.
- Встроенный оверлей статистики: время проходов, число draw call'ов, треугольников, память.
